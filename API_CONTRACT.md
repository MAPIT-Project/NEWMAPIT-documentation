# MAPIT API, SSE, and authentication contract

**Status:** current code baseline, with known contract violations  
**Last verified:** July 20, 2026  
**Scope:** contract between `webapp-ui/` and the FastAPI backend in `MAP-IT_SA/`

This document describes what the current code actually does. It does not guarantee that the API is safe for production. In particular, authentication and user isolation are not enforced by the V3 and V4 backend routes. See [SECURITY_REGISTER.md](SECURITY_REGISTER.md) and [KNOWN_ISSUES_AND_RISKS.md](KNOWN_ISSUES_AND_RISKS.md).

## 1. Base URLs and protocol

| Use | Base URL | Explanation |
|---|---|---|
| FastAPI, local process | `http://localhost:8000` | Default from `app/core/config.py` and `make run`/`make run-reload`. |
| FastAPI, Docker Compose from the host | `http://localhost:18000` | Host mapping of the backend container; this is also the default fallback for the SvelteKit proxies. |
| SvelteKit | `http://localhost:5173` | The browser uses the same-origin routes under `/api/...` whenever possible. |
| OpenAPI | `${BACKEND_BASE}/openapi.json` | Generated by FastAPI. OpenAPI describes the JSON routes, but not the different SSE payloads as a discriminated union. |

JSON requests use `Content-Type: application/json`, except for the multipart upload routes. Streaming routes return `text/event-stream`. All SSE frames contain only a `data:` line with a single JSON object and end with a blank line:

```text
data: {"type":"token","content":"tekst"}

```

No named SSE `event:` fields or heartbeat frames are sent. The client must therefore discriminate based on the JSON field `type`.

## 2. Authentication and user identity: current state

### 2.1 Actual flow

```text
Browser
  -> POST /api/auth/login (SvelteKit)
  -> Supabase Auth signInWithPassword
  <- Supabase-sessiecookies
  -> SvelteKit hook: supabase.auth.getUser() valideert de browsergebruiker

V3 streaming:
Browser -> SvelteKit streamingproxy
        -> getSession() controleert dat een sessie aanwezig is
        -> proxy maakt een eigen HS256-JWT met sub="webapp-proxy"
        -> FastAPI ontvangt Authorization-header, maar V3 gebruikt geen authdependency

V3 non-streaming/context en V4:
Browser -> transparante SvelteKit-proxy -> FastAPI
        (geen uniforme sessiecontrole en geen betrouwbare user-mapping)
```

The frontend login uses Supabase Auth. `hooks.server.ts` validates server-side with `supabase.auth.getUser()` and sets `event.locals.user`. This does not automatically secure every SvelteKit API route; a handler must check `locals.user` or Supabase itself.

`webapp-ui/src/lib/server/jwt.ts` can also create a MAPIT-specific HS256 token. This is not the same contract as a Supabase access token: among other things, the backend expects its own `type: "access"` claim and verifies it with `JWT_SECRET_KEY`. A Supabase token is not validated as such anywhere by FastAPI.

FastAPI does include `get_current_user`, role and tier dependencies in `app/core/auth.py`, but `app/main.py` does not register `AuthMiddleware`, and the V3/V4, feedback, document, and call routes described below do not use `Depends(get_current_user)`. Therefore, a supplied bearer token currently has no authorization effect there.

### 2.2 User ID contract

| Path | Actual source of identity | Risk/consequence |
|---|---|---|
| V3 message stream and non-streaming | Query parameter `user_id`, default integer `1` | The caller can choose the ID; if omitted, storage/analytics are associated with user `1`. The Supabase user ID is not mapped. |
| V3 context GET/DELETE | Only `conversation_id` from the path | No ownership check. |
| V4 create | Query parameter `user_id`, default string `default-user` | The caller determines the owner of an automatically created proposal. |
| Other V4 routes | Only `session_id`/`section_id` from the path | No check that the caller is the owner or a collaborator. |
| V3 streaming proxy | A Supabase session must exist, but the generated backend JWT has `sub=webapp-proxy` | The retrieved `session.user.id` is not used. The backend also ignores the JWT. |
| V3 non-streaming proxy and V4 catch-all proxy | No uniform authentication check | Direct and proxied calls can reach the open backend. |

**Contract status:** there is no implemented, reliable mapping `Supabase auth.users.id -> client.id -> FastAPI user_id`. Therefore, treat all V3/V4 data as not tenant-isolated until authn, authz, and ownership checks have been added to the code.

## 3. V3 Conversation API

Prefix: `/api/v3/conversation`  
Source: `MAP-IT_SA/app/api/conversation_routes_v3.py`

### 3.1 Models

`MessageRequest`:

```json
{
  "message": "Welke open Horizon Europe-calls passen bij circulaire bouw?",
  "include_context": true
}
```

`message` is required and is not validated for length or empty content in the Pydantic model. `include_context` is optional and defaults to `true`, but the route does not pass it to `ConversationManager`; therefore, the flag currently has no functional effect.

`MessageResponse`:

```json
{
  "response": "...",
  "metadata": {
    "architecture": "simplified_v3",
    "confidence": 0.82,
    "tools_used": ["search_funding_calls"]
  }
}
```

The contents of `metadata` are a free-form JSON object and may differ by agent path.

### 3.2 Endpoints

| Method and path | Input | Success response | Note |
|---|---|---|---|
| `POST /{conversation_id}/message/stream` | Body `MessageRequest`; query `user_id: int = 1` | SSE, HTTP 200 | Stores user/assistant messages and logs analytics. Errors after the stream has started are SSE events, not HTTP error statuses. |
| `POST /{conversation_id}/message` | Body `MessageRequest`; query `user_id: int = 1` | `MessageResponse` | Non-streaming. An unexpected error becomes HTTP 500. |
| `GET /{conversation_id}/context` | No body | `{conversation_id, message_count, messages, architecture}` | Reads up to 10 recent messages; no user/ownership filter. |
| `DELETE /{conversation_id}/context` | No body | `{success, message, conversation_id}` | Clears context via `clear_conversation`; no ownership check. |
| `GET /health` | No body | `{status, architecture, components, timestamp, errors?}` | Tests Redis, the database, and Gemini. A Gemini call of up to five seconds is part of this check. |
| `GET /analytics/summary` | Query `hours: int = 24` | `{success, period_hours, data}` | No bounds on `hours`, no auth. |
| `GET /analytics/low-confidence` | Query `threshold: float = 0.4`, `limit: int = 50` | `{success, threshold, count, conversations}` | No auth. |
| `GET /analytics/search` | Optional `query`, `conversation_id`, `min_confidence`, `max_confidence`; `limit=100`, `offset=0` | `{success, count, limit, offset, results}` | No Pydantic bounds on pagination parameters. |
| `GET /analytics/export` | Optional `start_date`, `end_date` in ISO format | `{success, count, start_date, end_date, data}` | An invalid date returns HTTP 400; no auth. |

There is no `POST /api/v3/conversation` for creating a conversation. Conversation records are managed by frontend/Supabase routes; the V3 backend expects an existing numeric `conversation_id`.

### 3.3 V3 SSE events actually emitted

| `type` | When | Payload fields |
|---|---|---|
| `status` | Processing stage | `stage`: `processing`, `context_loaded`, `agent_starting`, optionally `synthesizing`, `streaming_response`; `message: string`. |
| `conversation_name` | Only if there are no recent messages yet and name generation succeeds | `name: string`, `conversation_id: int`. |
| `agent_thinking` | Each ReAct iteration | `iteration: int`, `thought: string`, `action: string`. Note: this exposes agent reasoning to the client. |
| `tool_call` | Before tool execution | `iteration`, `tool_name`, `display_name`, `parameters: object`, `reasoning`. |
| `tool_result` | After tool execution | `iteration`, `tool_name`, `success`, `result_count`, `result_summary` (up to approximately 300 characters), `execution_time_ms`. |
| `token` | After the complete response has already been constructed | `content: string`; the manager splits the response into blocks of 50 characters. This is simulated output streaming, not a provider token stream. |
| `complete` | Normal end | Top-level `ai_provider`, `ai_version`, `model_used`, `data_source`, `processing_time`, `projects_found`, `logs`; `metadata` with `architecture`, `confidence`, `tools_used`, `processing_time_ms`. |
| `error` | Agent, storage, or route error | At minimum `error: string`; sometimes `stage: "error"`; for a storage error, also `response`. A storage error may be followed by tokens and `complete`. |

The V3 route has `progress` in an internal allowlist, but none of the reviewed producers emit this type. The internal `agent_complete` from `ToolAwareAgent` is processed by `ConversationManager` and is not sent directly to the V3 client.

Example:

```bash
curl -N -X POST \
  'http://localhost:8000/api/v3/conversation/123/message/stream?user_id=1' \
  -H 'Content-Type: application/json' \
  -d '{"message":"Zoek open calls voor groene waterstof","include_context":true}'
```

A bearer header is not currently required for this endpoint and does not change the backend identity.

## 4. V4 Proposal Session API

Prefix: `/api/v4/proposal-session`  
Source: `MAP-IT_SA/app/api/proposal_session_routes.py`

The older prefix `/api/v4/proposals/sessions`, documented elsewhere, does not exist.

### 4.1 Request models

| Model | Fields |
|---|---|
| `CreateSessionRequest` | `proposal_id: int` required; `call_id: string` required; `title: string` required; `proposal_type: string = "RIA"`; `conversation_id: int|null = null`. |
| V4 `MessageRequest` | `message: string` required; `section_context: string|null = null`. |
| `SectionUpdateRequest` | `content: string` required. |
| `SectionStatusRequest` | `status: string` required. The actual valid values are `empty`, `draft`, `in_review`, `complete`; any unknown value silently becomes `draft`. |
| `SectionGenerateRequest` | `guidance: string|null = null`; `word_target: int = 500`; `style: string = "formal"`. There are no minimum/maximum bounds. |

`SessionResponse` contains:

```json
{
  "session_id": "uuid",
  "proposal_id": 42,
  "call_id": "HORIZON-CL5-2026-01-D2-01",
  "title": "GREENLOOP",
  "proposal_type": "RIA",
  "status": "active",
  "active_section_id": null,
  "completion_percentage": 0.0,
  "total_words": 0,
  "sections": {
    "excellence": {
      "section_id": "excellence",
      "section_name": "...",
      "content": "",
      "word_count": 0,
      "quality_score": null,
      "status": "empty",
      "suggestions_count": 0,
      "gaps_count": 0,
      "lock_status": "unlocked",
      "is_dirty": false,
      "version": 1,
      "last_updated": null
    }
  },
  "created_at": "2026-07-20T10:00:00+00:00"
}
```

### 4.2 Endpoints

| Method and path | Input | Success response |
|---|---|---|
| `POST /create` | Body `CreateSessionRequest`; query `user_id: string = "default-user"` | `SessionResponse`. If `proposal_id` does not exist, a proposal is created; the resulting ID may therefore differ. |
| `GET /{session_id}` | No body | `SessionResponse`; 404 if not found. |
| `DELETE /{session_id}` | No body | `{"success":true,"message":"Session deleted"}`. |
| `POST /{session_id}/message/stream` | Body V4 `MessageRequest` | SSE with agent and session state events. |
| `POST /{session_id}/message` | Body V4 `MessageRequest` | `{response, sections_affected, tools_used, confidence, metadata:{architecture,iterations,proposal_intent}}`. |
| `PATCH /{session_id}/section/{section_id}` | Body `SectionUpdateRequest` | `{success, section_id, word_count, status, quality_score}`; HTTP 400 when locked/on failure. |
| `PATCH /{session_id}/section/{section_id}/status` | Body `SectionStatusRequest` | `{success, section_id, status}`. |
| `POST /{session_id}/section/{section_id}/generate` | Body `SectionGenerateRequest` | SSE; see the separate schema below. |
| `POST /{session_id}/section/{section_id}/evaluate` | No body | Tool result as a free-form JSON object; on success, includes `evaluated` and `score`, among other fields. There is no response model that validates this contract. |
| `POST /{session_id}/section/{section_id}/analyze-gaps` | No body | Tool result as a free-form JSON object. There is no response model. |
| `POST /{session_id}/focus/{section_id}` | No body | `{success:true, active_section_id}`; 404 for an unknown session/section. |
| `GET /health` | No body | Intended: `{status, architecture, components, errors, timestamp}`. See the route conflict below. |

**Verified route error:** `GET /{session_id}` is defined before `GET /health` and accepts any string. Due to Starlette/FastAPI route ordering, `/api/v4/proposal-session/health` is therefore treated as session ID `health`. The health handler is currently effectively unreachable through that path and generally returns `NOT_FOUND` instead of component health.

### 4.3 V4 chat SSE

`POST /{session_id}/message/stream` can pass through the following events that are actually emitted:

| `type` | Payload fields |
|---|---|
| `status` | `stage`, `message`; agent status also contains `proposal_intent`. There are two initial processing statuses: one from the route and one from the agent. |
| `agent_thinking` | `iteration`, `thought`, `action`. |
| `tool_call` | `iteration`, `tool_name`, `display_name`, `parameters`, `reasoning`. |
| `tool_result` | `tool_name`, `success`, `result_count`, `execution_time_ms`. |
| `section_update` | `section_id`, `tool_name`, `content`. The route writes the full content to session state while the section is temporarily locked. |
| `agent_complete` | `result` with `answer`, `success`, `sections_affected`, `iterations`, `confidence`, `total_time_ms`, `proposal_intent`. |
| `session_state` | Final event with `completion_percentage`, `total_words`, `sections_affected`. |
| `error` | `error: string`. An unknown session is also reported this way within an HTTP 200 stream. |

Despite the route docstring, this chat path currently does not emit `token` events: the full response is in `agent_complete.result.answer`. The frontend types also mention `chunk`, but the reviewed V4 producer does not emit it.

`POST /{session_id}/section/{section_id}/generate` has a separate, smaller event contract:

| `type` | Payload fields |
|---|---|
| `status` | `message`, `section_id`. |
| `content` | `section_id`, full `content`. |
| `complete` | `section_id`, `word_count`. |
| `error` | `error`. |

Create and chat example:

```bash
curl -X POST 'http://localhost:8000/api/v4/proposal-session/create?user_id=demo-user' \
  -H 'Content-Type: application/json' \
  -d '{
    "proposal_id": 42,
    "call_id": "HORIZON-CL5-2026-01-D2-01",
    "title": "GREENLOOP",
    "proposal_type": "RIA"
  }'

curl -N -X POST \
  'http://localhost:8000/api/v4/proposal-session/SESSION_UUID/message/stream' \
  -H 'Content-Type: application/json' \
  -d '{"message":"Schrijf een eerste versie van excellence","section_context":"excellence"}'
```

## 5. Other mounted core endpoints

These routes are mounted in `app/main.py` and likewise do not use the backend auth dependency.

### 5.1 Feedback — prefix `/api/feedback`

| Method and path | Input | Response |
|---|---|---|
| `POST /api/feedback` | JSON: required `conversation_id: string`, `rating: 1..5`, `feedback_type: string`; optional `feedback_text`, `message_id`, `query_text`, `response_text`, `tools_used`, `query_type`, `response_time_ms` | `{success, feedback_id?, message?, error?}`. `feedback_type` is only described, not validated as an enum. `response_text` is limited to 500 characters when stored. |
| `GET /api/feedback/summary?days=30` | `days` 1..365 | Free-form aggregation object. |
| `GET /api/feedback/conversation/{conversation_id}` | Path ID | `{conversation_id, feedback, count}`. |
| `GET /api/feedback/suggestions` | None | Free-form suggestion object/array. |
| `GET /api/feedback/health` | None | `{status, enabled, message}`. |

### 5.2 Document ingestion — prefix `/api/documents`

| Method and path | Input/summary |
|---|---|
| `POST /upload` | `multipart/form-data`: `file` required; optional `document_type`, `programme_year`, `metadata` as a JSON string. Supported extensions and the default limit (50 MB) come from backend settings. Processing starts as an in-process background task. |
| `POST /ingest-url` | Query parameters `url`, optional `document_type`, `programme_year`; optional JSON body parameter `metadata`. Only a fixed list of EU domains is accepted. |
| `GET /list` | `limit=50` (1..100), `offset=0`, optional `status`, `document_type`. |
| `GET /{document_id}` | Optional `include_chunks=false`. |
| `GET /{document_id}/status` | Ingestion status. |
| `POST /{document_id}/reprocess` | Starts background reprocessing. |
| `DELETE /{document_id}` | Deletes the database object and attempts to delete the local file. |
| `GET /{document_id}/chunks` | `limit=50` (1..100), `offset=0`. |
| `GET /stats/overview` | Document statistics. |
| `POST /batch-upload` | Multipart `files`; maximum of ten; invalid files are skipped. |

**Route ordering risk:** `GET /{document_id}` is declared before `GET /stats/overview`. A request to `/api/documents/stats/overview` has two segments and therefore does match the specific stats route; there is no conflict here. However, uploads are accessible without auth and write to local storage.

### 5.3 Call documents — prefix `/api/call`

| Method and path | Input | Response |
|---|---|---|
| `POST /{call_id}/ask` | Body `{question: string, call_id?: string|null, max_chunks: int = 10}` | `{answer, call_id, chunks_used, sources: string[], cached, processing_time_ms}`. The body `call_id` is not used; the path value takes precedence. No bounds on `max_chunks`. |
| `GET /{call_id}/documents` | Path ID | `{call_id, documents_count, chunks_count, cached, documents}`. |

The ask route uses a hardcoded model name `gemini-2.0-flash-exp` and returns 500 when the database pool or Gemini cannot be initialized.

### 5.4 Proposal documents

In addition to V4, a separate CRUD API exists under `/api/proposal-document` (`proposal_document_routes.py`) for live document editing. The SvelteKit routes `/api/proposal-document` and `/api/proposal-document/[...path]` proxy to it. This is a second proposal contract alongside the V4 session state; IDs and state must be kept consistent by the caller. The routes have no FastAPI auth dependency or ownership filter.

## 6. SvelteKit proxy matrix

| Browser path | Backend path | Auth behavior |
|---|---|---|
| `/api/proxy/conversation/{id}/message/stream` | `/api/v3/conversation/{id}/message/stream` | Checks Supabase `getSession()`, but not `getUser()`; creates a proxy JWT; does not pass `user_id`, so the backend uses `1`. |
| `/api/proxy/conversation/{id}/message` | `/api/v3/conversation/{id}/message` | No session check; forwards only the JSON Content-Type; the backend uses `user_id=1`. |
| `/api/proxy/conversation/{id}/context` GET | `/api/v3/conversation/{id}/context` GET | No session check. |
| `/api/proxy/conversation/{id}/context` POST | Nonexistent backend `POST .../context` | Contract violation; generally expected to return HTTP 405. |
| `/api/proxy/conversation/{id}/reset-context` POST | `/api/v3/conversation/{id}/context` DELETE | No independent session check. |
| `/api/v4/[...path]` | `/api/v4/{path}` | Transparent catch-all; no independent session/ownership check. |

The frontend uses `BACKEND_URL`, with fallback `http://localhost:18000`. A browser client should use these same-origin proxies and should not expose the FastAPI port publicly; however, this is currently only deployment guidance, not backend security.

## 7. Error contract

For regular JSON routes, the global FastAPI handlers replace standard `HTTPException` and validation errors with:

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Request validation failed: 1 error(s)",
  "recoverable": false,
  "suggestion": "Please check your input and ensure all required fields are provided in the correct format.",
  "details": {
    "validation_errors": [
      {"field": "body -> message", "message": "Field required", "type": "missing"}
    ]
  }
}
```

Possible optional fields are `suggestion`, `details`, and `request_id`. Every HTTP response receives an `X-Request-ID` header through middleware. However, many route handlers catch internal exceptions and put the raw exception text in `HTTPException(detail=...)`; the global handler then publishes it as `message`. This may leak implementation details.

SvelteKit proxies do not use the same schema: responses there include `{error: string}`, SvelteKit error responses, and unchanged backend responses, among others. SSE errors always use an event such as `{"type":"error","error":"..."}` and usually retain HTTP 200 because the headers have already been sent.

## 8. Compatibility and change rules

- Do not add a V3/V4 event type or required field without changing the frontend type and parser at the same time.
- Preserve unknown SSE events client-side for forward compatibility: log them and safely ignore them.
- Treat free-form tool results (`evaluate`, `analyze-gaps`, feedback aggregations) as unstable until response models have been introduced.
- Explicitly treat the auth/identity change as a breaking change: after the fix, `user_id` must come exclusively from a validated principal and no longer from a caller query parameter.
- Add contract tests for the five proxy paths in the matrix, with particular attention to SSE, HTTP errors, and session/ownership denial.
